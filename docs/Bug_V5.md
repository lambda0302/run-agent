## UX：Plan 拒绝语义失效（V5-1）

- **现象**（真实会话 2026-08-11）：用户对 `exit_plan_mode` 弹窗按 `n` 拒绝后，模型行为错误——第一版把实现内容当文本 dump 出来；第二版循环调用 `enter_plan_mode` → `exit_plan_mode` 重新呈现同一计划，不停下来等用户命令（用户期望的是 Claude Code 式「先停下，等待下一条指令」）。
- **根因**：拒绝路径回填给模型的是一句**通用** `权限被拒绝: 未授权执行 exit_plan_mode`，模型把「权限拒绝」误读为「自身状态错误」（误以为没在 plan / 需要重进），于是反复重试。拒绝语义根本没有传达给模型。
- **第一轮修复（不充分）**：只在系统提示注入「计划被拒 → 立即停止并等待用户下一条指令，不输出实现内容、不重复尝试执行」。用户复测发现模型仍重呈现计划——静态指引压不过工具结果里那句通用「权限被拒绝」，模型只信实时回填。
- **最终修复**（0.5.1，commit `4874fce`）：`Tool` 新增可选 `denyMessage`；`execute.ts` deny 路径回填 `tool.denyMessage ?? 通用消息`；`exit_plan_mode` 装配专属消息「用户拒绝了你的计划。立即停止当前工作，不要再次调用 enter_plan_mode 或 exit_plan_mode，等待用户下一条指令；若用户有修改意见，按其指示调整后再重新呈现计划」。**双保险 = 系统提示引导 + 拒绝回填语义**。复测通过：按 `n` 后模型正确回「已停止，请告诉我你的修改意见」。
- **教训**：拒绝/失败类回填文本是模型行为的关键输入——通用「权限被拒绝」会把用户意图误传成状态错误。**工具可以装配专属 `denyMessage`**；UX 语义问题优先在工具结果里显式传达，系统提示只是兜底，压不过实时回填。

## 显示：权限弹窗被后台并行工具结果污染（V5-2）

- **现象**（真实会话 2026-08-11）：权限确认弹窗（`y/n/a`）激活期间，弹窗前已入队的后台只读工具完成，`└ 工具结果` 直接打印在提示行上——看起来像「卡住」/「输入被吞」，实际是在等输入。
- **根因**：V5 StreamingToolExecutor 让工具「流式边执行」——`addTool` 里先 `onToolCall`（打 ⚡）再入队，工具本体 fire-and-forget，完成后 `onToolResult` 直写 `out`。权限弹窗时流式循环阻塞在 `await addTool → checkPermission → ask`，但已启动的后台工具仍可完成打屏；`rl.question` 期间没有任何输出缓冲。
- **修复**（0.5.1，commit `4874fce`）：新增 `createOutputGate`——`ask` 弹窗前 `gate.begin()`（后续 agent 输出入缓冲），答完 `gate.end()` 按序刷出；`createHandlers` 全部经 `gate.emit` 路由。one-shot 不经门（无弹窗），行为不变。测试 `tests/cli/output-gate.test.ts` 锁定（弹窗期间缓冲、结束后按序刷出、恢复直写）。
- **教训**：流式并行 + 同步弹窗交互并存时，**输出必须有「弹窗期缓冲」边界**；显示交错会让用户误判为卡死，比功能 bug 更伤信任。`rl.question` 直接写 `output`，弹窗文本本身不该进门。

## 排查：陈旧进程读取 `.run-agent` 未拒绝（V5-3）

- **现象**（真实会话 2026-08-11）：某会话里 `read_file F:\MyClaudeCode\.run-agent\mcp.json` 返回「读取失败: 文件不存在」而非权限拒绝——而当前引擎对 `.run-agent` 路径段是内置 deny。
- **排查**：逐层核对——权限引擎（`.run-agent` 段 deny，`tests/permissions/engine.test.ts:219`）、工具层（read_file/glob/grep 的 ALWAYS_IGNORE，`glob.test.ts:71` / `grep.test.ts:50`）、全局 `run-agent`（实为指向本地仓库的符号链接）。当前代码全部正确拒绝。用临时 repro 测试 + 用户新会话复测确认：**当前构建对 `.run-agent` 的 read_file / run_bash / glob / grep 全部拒绝，模型也如实说不臆造内容**。
- **根因**：该会话进程在 dist 重建（当天 23:05）**之前**启动，跑的是旧构建。属陈旧进程误报，非当前代码缺陷。
- **状态**：已排除。教训：**复测安全边界务必新起会话**——旧进程跑旧代码是误报源；`.run-agent` 的 deny 是内置底线，引擎与工具层都有常驻测试。

## 产品缺口：run-agent 不自带自文档（V5-4）

- **现象**（真实会话 2026-08-11）：用户让 run-agent 自己配置 GitHub MCP，模型找不到官方文档，只能逆向 grep / 读已安装的 `dist/cli.js` 推配置格式，烧了 ~12 个权限确认才定位到 `~/.config/run-agent/mcp.json`。
- **根因**：① `package.json` `files: ["dist"]` → npm 发布包**不带 `docs/`**，真实安装里 `docs/mcp.md` 物理不存在；② system prompt 没有任何「run-agent 自身配置文档在哪」的指针（CLAUDE.md 里那句「详见 docs/mcp.md」模型在 cwd 外也读不到）。
- **对照**：模型不是思路跑偏——对黑盒安装，逆向读 bundle 是唯一可靠路径；是产品缺「自文档」。开发环境下 docs 其实在包根（符号链接），但模型没有理由知道。
- **处理**：两个提案待用户拍板，未实施——**A**（发布包带 docs：`files` 加 `docs` + system prompt 注入自文档指针，两行改动）；**B**（`run-agent mcp add` 交互向导直接写 mcp.json，真正终点）。
- **教训**：自指工具（agent 配置 agent 自己）要有「自己文档在哪」的显式注入，否则只能逆向；发布包内容（`files`）与「模型能否自助」直接相关。

## 小结

- **真 bug 2 个**（V5-1 拒绝语义、V5-2 显示交错），都是 0.5.0 发布后**真实使用暴露**，随 0.5.1 修复；**误报 1 个**（V5-3 陈旧进程，已排除）；**产品缺口 1 个**（V5-4 自文档，待改进）。
- **共性教训**：① 拒绝/失败回填文本是模型行为的关键输入，需装配专属 `denyMessage`，别只靠通用「权限被拒绝」。② 流式并行 + 弹窗并存必须有输出缓冲门，显示交错会误判为卡死。③ 复测安全边界新起会话，旧进程跑旧代码是误报源。④ agent 配置 agent 自身需要有自文档指针。
- **非产品 bug（不列入表）**：V5-3 属环境误报；Plan_V5.md §4 的风险（MCP 参数黑盒、plan 死锁、执行器回归）在实施期已被设计规避，未转化为实际 bug。
